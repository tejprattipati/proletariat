# Google server integration

This module is server-only. Import `getGoogleStatus`, `executeGoogleAction`, `isGoogleAction`, and `configureGoogleIntegration` from `index.ts`; do not bundle these files into the GitHub Pages frontend. The backend mounts `createGoogleRouter({ authorizeRequest, getPermissions, getIntegration })` from `server/google-router.ts` at `/api/google`. The contract also exports `googleRouter`, which denies requests until `configureGoogleRouter` supplies its hooks.

## Deployment configuration

The owner supplies a Google Web application OAuth client. Enable the Drive, Gmail, Calendar, Docs, and Sheets APIs used by the selected capabilities. Register the exact backend callback, for example `http://127.0.0.1:3001/api/google/callback` locally or `https://<backend-host>/api/google/callback` in a deployment. HTTPS is required except on loopback. Public Google scopes may require consent-screen verification; test users and workspace policy can affect which grants are available.

Server environment:

| Setting | Requirement |
| --- | --- |
| `GOOGLE_CLIENT_ID` | Web OAuth client ID supplied by the owner |
| `GOOGLE_CLIENT_SECRET` | Matching client secret; server only |
| `GOOGLE_REDIRECT_URI` | Exact registered backend URL ending in `/api/google/callback` |
| `TOKEN_ENCRYPTION_KEY` | Stable base64-encoded 32-byte key used by the lead's encrypted database token store |
| `DATA_DIR` | Private persistent runtime storage; use an absolute directory outside the repository for live deployment |
| `GOOGLE_IDENTITY_REDIRECT_URI` | Separately registered app sign-in callback, ending in `/api/identity/callback` |
| `GOOGLE_IDENTITY_CLIENT_ID` / `GOOGLE_IDENTITY_CLIENT_SECRET` | Optional separate identity client; the backend otherwise uses the data client values |
| `FRONTEND_URL` | Exact trusted frontend URL for the backend identity handoff |
| `CORS_ORIGIN` | Explicit allowed frontend origins; credentialed OAuth setup must use the real frontend origin |
| `VITE_API_URL` | Public backend origin compiled into the Pages frontend; never place secrets in any `VITE_` variable |

No credentials are generated by this module's setup. It never reads browser, ChatGPT, or preexisting third-party credentials. OAuth access/refresh tokens must be encrypted at rest and must never be serialized in public workspace state, responses, logs, fixtures, or the repository. An optional `EncryptedFileTokenStore(absolutePath, base64Key, repositoryRoot)` is available for a single-account backend; it rejects repository paths and uses AES-256-GCM plus owner-only file permissions. Production currently uses the lead's injected encrypted database store.

## Private setup for personal use

These are owner actions, not actions performed by the assistant. Do not create a client or expand an existing grant automatically. The application cannot reuse a ChatGPT Google connector or a ChatGPT/Codex session as Google OAuth credentials.

1. Choose an owner-controlled Google Cloud project and explicitly enable only the APIs needed for the approved work: Gmail and Calendar for Daily, plus Drive/Docs/Sheets for selected attachments. No Google API key or service account is used by this adapter.
2. In Google Auth platform, configure Branding and Audience. A personal Google account uses External; while Testing, add the owner's chosen Google account under Test users. Use Internal only when the Google Workspace organization supports it. Review the applicable data policy before agreeing.
3. In Data Access, add the exact approved scopes. For reads: `gmail.readonly`, `calendar.events.readonly`, `drive.readonly`. Docs/Sheets content reads use the Drive read grant and do not require write scopes. Keep draft, send, bulk-send, Docs writes, Calendar writes and Drive writes disabled unless separately approved. Full-read app toggles are an additional application boundary, not a substitute for OAuth consent.
4. In Clients, create or select a **Web application** client and register the exact Express callback. The local example is `http://127.0.0.1:3001/api/google/callback`; a hosted callback uses the backend HTTPS origin. GitHub Pages is the frontend and never hosts the callback or secrets.
5. Supply the server environment listed above through private local/deployment configuration. Reuse a securely supplied encryption key; losing or changing it prevents reading existing encrypted tokens. This implementation does not generate or print keys, client secrets, access tokens or refresh tokens.
6. Sign in to the backend with a verified Google identity, enable the approved application permissions, and deliberately choose Connect Google. Review Google's account and scope consent screen. A connection with partial consent is accepted only for its actual granted scopes. Missing scopes produce a setup error; the adapter never silently authorizes more access.
7. For Daily, choose the Gmail query, calendar and timezone before reading. `newer_than:1d` is a Gmail search query, not an exact local-day filter. Calendar reads use the selected local date, including daylight-saving transitions. For a selected Drive attachment, choose/bind one accessible file; browse results alone are not attachment authorization.

Google's current setup guidance: [web-server OAuth](https://developers.google.com/identity/protocols/oauth2/web-server), [consent configuration](https://developers.google.com/workspace/guides/configure-oauth-consent). Gmail read/compose and broad Drive scopes are restricted scopes; public OAuth distribution may require verification/security assessment under Google's rules. A public code repository does not itself authorize a user's private data. See [Gmail scopes](https://developers.google.com/workspace/gmail/api/auth/scopes) and [Drive scopes](https://developers.google.com/workspace/drive/api/guides/api-specific-auth).

## Daily and attachment integration

`daily.read {date?,gmailQuery?,calendarId?}` returns a bounded `state.daily`, independent Gmail/Calendar/Drive provider statuses and actual source IDs. Disconnected and disabled providers remain visible. Each invocation processes one provider page; repeat with the same inputs to continue it. A provider failure preserves the other provider and the failed provider's saved page boundary. Completed Gmail reads re-enumerate the exact query and reuse authorized cached bodies: Gmail history cannot safely substitute for a relative search query. Calendar adopts `nextSyncToken` only on the final complete page, omits incompatible day-filter parameters on delta requests, and rebuilds the bounded day after an expired token. Changed/deleted or moved-out events update the snapshot. Daily events receive current-grant bindings so an explicit later Calendar edit can be separately authorized. Source IDs use the verified data-account identity so same-account reconnects retain canonical provenance; cache, operation and binding stores remain grant scoped.

Source text is untrusted data. Gmail uses MIME plain text where available and converts HTML to plain text without scripts, external loads or binary attachment inference. A snippet is never counted as a full body. Calendar descriptions are bounded plain text. No task interpretation or model calls occur in this adapter; the lead owns explicit `Task:/Todo:/Action:` extraction and model context construction. Daily receipts link the exact input sources and label continued/bounded reads as pending rather than successful full coverage.

`attachment.read {resourceId}` requires a bound live file verified under the current OAuth grant, plus current `driveRead`. It returns one `Attachment` in `state.attachments` and its `entityId`. Docs tabs/named ranges and Sheets gids/named ranges stay tied to stable IDs. Native Docs/Sheets API calls accept read-only Drive access. UTF-8 text/CSV/JSON/XML/HTML and PDF use bounded Drive media reads. Unsupported formats and missing PDF extraction are explicit attachment errors. Output text is at most 40,000 characters with `truncated` when needed; selected media downloads are at most 5 MiB. Each API JSON response is separately bounded. Binary source bytes are not persisted in attachment records.

The lead must inject `GoogleDependencies.extractPdfText(bytes): Promise<{text,truncated}>` from its shared local-upload parser. Local PDF/DOCX/text uploads, upload/conversation authorization and conversation membership are the lead's routes, not Google routes. The lead must filter/reset old Google-derived chat context after disconnect or grant change; this adapter independently rejects old bindings and scopes before cache replay.

Disposable read caches are grant-scoped, expire after five minutes (Drive metadata after one minute), and retain at most 256 entries/16 MiB in normal single-worker operation. They never evict send journals, OAuth state, bindings or resumable scan cursors. Daily retains at most 30 records per grant, 500 sources/2,000,000 source characters per snapshot, and 500 events/1,000,000 Calendar characters per record. Individual Calendar text is bounded to 40,000 characters. Reaching a bound produces a visible partial/truncated status and does not claim full coverage or advance an incomplete Calendar sync token. Existing snapshots/cursors are schema-versioned; runtime records remain private. Retention is separate from the exact context budget passed to any later model.

## Sign-in and multi-user integration boundary

The current backend uses the lead's `/api/identity/*` session/handoff routes. Configure `GOOGLE_IDENTITY_REDIRECT_URI`, for example `http://127.0.0.1:3001/api/identity/callback`, and `FRONTEND_URL`, alongside the separate data callback `GOOGLE_REDIRECT_URI`. Optional `GOOGLE_IDENTITY_CLIENT_ID` and `GOOGLE_IDENTITY_CLIENT_SECRET` select a different Web client for app identity. `GoogleSignIn` / `signInConfigFromEnv` are reusable identity-only server helpers; their optional legacy router uses `GOOGLE_SIGNIN_REDIRECT_URI` ending in `/api/google/signin/callback`, which the current backend does not mount. Registering a callback grants no data access. Login requests exactly `openid email`, online access and no incremental data-scope union. Google access/refresh tokens returned by this login are discarded. Any Google account with a verified token can sign in; there is no repository email allowlist and email matching never links Google and ChatGPT authorization.

The maintained Google verifier checks the RSA signature against bounded, cached Google certificates, issuer, audience and lifetime. This module also requires a verified email, stable nonempty subject, authorized-party match when present, and the OIDC nonce from the browser-bound one-time state/PKCE flow. The stable identity key is issuer plus subject, not email. Raw ID tokens and codes are not returned or persisted as sessions. See [Google OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect) and [server ID-token verification](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token).

Use `createGoogleRouter` with optional `signIn: {service, establishSession, redirectAfterSignIn?}`. It owns GET `/api/google/signin` and `/api/google/signin/callback`; the lead supplies the opaque HttpOnly server session in `establishSession(identity,request,response)` only after verification. New login routes return a setup error until that hook is configured. `redirectAfterSignIn` is a trusted server constant, never an arbitrary request redirect. The default exported router remains a legacy personal integration route; use the factory for sign-in.

With sign-in configured, data routes fail closed unless the lead also supplies `getIntegration(request)` resolving a **user-owned** `GoogleIntegration`, and `getPermissions(request)` / `authorizeRequest(request)` from that verified session. Do not point these hooks at the personal singleton or the owner's workspace. Per-user adapter dependencies must independently own token storage, Google key/value/operation storage, current permissions and their workspace/job queue. Configure `identityVerifier` and `getAuthenticatedSubject` together: data OAuth then verifies an ID token/nonce before saving the grant, binds its independently selected verified data subject/email to the initiating application `ownerSubject`, and rejects grants owned by another app user before API calls/cache reads. The data account may differ from app identity and ChatGPT. Refreshes preserve both identities, never matching by email. Existing user-owned grants lacking `ownerSubject` require reconnection. The account chooser is explicit and the status label names the selected data account. The identity-only flow and explicit data-connection consent remain separate.

This lane tests ID-token checks, distinct subjects, separate route adapters/stores and mismatched data grants. The lead owns session/CSRF, per-user workspace/task/conversation/upload/job isolation and explicit user-owned ChatGPT account authorization. **Do not publicly enable multi-user access until those aggregate isolation tests pass.** The old personal singleton and local Codex session must never serve another user's requests. No matching email or Google sign-in establishes ChatGPT consent. If the supported plan bridge is personal/local only, keep that deployment restriction visible instead of sharing a host account.

## Required persistence hooks

`GoogleDependencies` in `contracts.ts` requires a token store and a durable Google store. `getPermissions()` is required for all provider API access, including cached reads and writes. Tests can additionally inject `fetch` and `now`.

- `tokenStore.load/save/clear`: use encrypted storage. Preserve every token field, including `connectionId`.
- `store.get/set/delete`: persist scans, cache entries, pagination cursors and OAuth state outside source control. A single `set` must replace its record atomically.
- `store.reserveOperation(key, fingerprint)`: atomically create a durable `pending` record, returning the existing record on collision. Never replace an existing fingerprint. Reservation must survive a process crash before returning.
- `store.finishOperation`: atomically replace the pending record with the observed accepted/failed/unknown outcome. Never expire or automatically reset send reservations.
- When a newly authorized `connectionId` differs from the stored grant, pause scheduled/running live campaigns, queued/running scans and automatic workflows before saving the new grant. The lead's SQLite implementation does this transactionally.

The integration serializes its own calls within a process. The lead must still serialize and persist workspace actions, save every `ActionResult`, and operate one backend/worker instance. This is a single-owner implementation, not a multi-user OAuth service.

## OAuth endpoints

Authenticated `POST /api/google/authorize` returns `{url}`. Navigate to that one-time backend start ticket; its first-party GET establishes an HttpOnly, SameSite=Lax callback cookie and redirects to Google. It avoids relying on third-party cookies from a cross-site Pages fetch. Ticket lifetime is one minute; OAuth state lifetime is ten minutes. Start tickets are process-local, so a server restart requires restarting consent.

The callback validates browser binding, one-time state, expiry, and PKCE before exchanging the code. Consent uses offline access and incremental scopes; the granted scope response is authoritative. Starting a new authorization or disconnecting invalidates an older pending authorization. Refreshes preserve refresh tokens and are serialized. Callback responses never contain token material.

Authenticated `GET /api/google/status` returns connection metadata. `POST /api/google/disconnect` deletes local tokens before attempting Google revocation. If revocation is not confirmed, the response explicitly says local tokens were removed and Google Account permissions need checking. GET disconnect is not supported.

## Capability and scope boundaries

| App permission | OAuth scope |
| --- | --- |
| `driveRead` | `drive.readonly` |
| `driveWrite` | `drive` (new native copies in selected destinations only) |
| `gmailRead` | `gmail.readonly` |
| `draft` | `gmail.compose` |
| `send` | `gmail.send` |
| `calendarRead` | `calendar.events.readonly` |
| `calendarWrite` | `calendar.events` |
| `docsWrite` | `documents` |

These are suffixes under `https://www.googleapis.com/auth/`. `driveFull`/`gmailFull` additionally permit broad scans; they do not independently authorize reads. `bulkSend` additionally permits campaign dispatch. Google scopes can be broader than an app capability: Gmail compose includes sending at Google's boundary, so the server independently checks `send` before any actual send. Changing a toggle does not grant an OAuth scope; reconnect when new scopes are needed.

Every integration action checks its supplied workspace permissions and the latest persisted permission flags. The transport rechecks relevant flags and granted scopes before each request. Caches, operation records, scan cursors and object bindings are isolated to one authorization grant. Reconnecting requires rebinding resource outputs, recreating old drafts, or rereading Calendar events; old grant IDs cannot silently target a different account.

## Action and worker behavior

- `resource.bind` verifies Google file metadata and resolves supported Drive/Docs/Sheets links without fetching arbitrary URLs. Resources use `google:drive:<fileId>`, retain document tab / sheet gid / managed named-range IDs, and have canonical direct URLs. Shortcuts resolve to their target file. Binding requires an explicit Google ID or link; this adapter does not guess files from ambiguous names.
- `resource.browse` accepts `parentId`, `q`, and optional `nextPage: true`. The next page cursor stays on the server per grant, parent and query. Each page merges into workspace resources. The message contains `More results are available.` only when another page exists. Authenticated `GET /api/google/resources` also exposes a typed paginated raw Drive metadata response.
- `scan.start`/`scan.resume` process one provider page per call, then return control. The worker must keep advancing queued/running jobs and respect paused jobs. Selected Drive coverage includes bound folder descendants; selected Gmail coverage includes explicitly linked live draft threads. Broad coverage requires the corresponding full-read flag. Drive scans extract supported document, spreadsheet, text and PDF contents into bounded private cache entries and resource excerpts. Folder metadata does not count as a content read; unsupported bodies are explicitly skipped. `read`/`contentRead` count extracted bodies, `metadataRead` counts Drive metadata, and `truncated` counts bounded excerpts. Gmail scans extract MIME text bodies; snippet-only responses are failures rather than content reads. `analyzed` remains zero because no model analysis occurs here.
- Each scan page stores its changed resources/content excerpts and progress with its cursor. On resume or the next sync, an uncommitted page is replayed before advancing, so a crash between adapter and workspace saves does not silently skip that page. A partially failed page is rolled back in workspace state and can be reread safely.
- `sync.run` uses Drive change tokens or Gmail history IDs once a complete broad scan has a checkpoint. Expired incremental history clears that checkpoint and returns `SYNC_CURSOR_EXPIRED`; an explicit new scan is required. A selected scan never silently expands to all data.
- Gmail primitives include message/thread reads, draft create/update, draft send and raw message send. MIME headers reject injection, and text is encoded as UTF-8/base64. Sending a draft submits the exact locally authorized content, avoiding sending an externally changed draft body or recipient.
- `draft.create/update`, `calendar.upsert`, and `docs.write` require `requestId`. The lead supplies one for every API action. Reusing a write identifier with different content fails. The journal also keys sends by draft or campaign-recipient ID so a new request ID cannot bypass a previous uncertain send.
- `campaign.start/resume` sends at most one pending unique recipient per call, with a persistent 1–60 messages/minute limiter. The worker must call again at the allowed interval while status is `running`. Scheduled campaigns wait until their time; unknown recipients pause the campaign. Permissions are checked after queue creation and again immediately before dispatch.
- `calendar.upsert` uses deterministic Google event IDs for creates and existing external IDs for updates. Timestamps must carry a timezone offset. Attendee notification emails are disabled with `sendUpdates=none`. `calendar.read` and `provider.listEvents` support bounded paginated reads using the independent read-only Calendar capability. Writes separately require `calendarWrite`.
- `docs.write` only updates a preexisting managed named range in a bound live Google document with `role: output`. Bind `namedRangeId`, plus `tabId` when the document has multiple tabs. The adapter fetches the current revision, confirms that the named range exists in that tab, then sends `replaceNamedRangeContent` with `requiredRevisionId`. It never replaces the entire document or guesses a target tab/range.

## Reusable document recipes

Recipes persist their exact bound `referenceResourceId` and `destinationFolderId` in the shared workspace. The domain handles recipe creation/update; this module handles live `recipe.run {id,title,context,person?,taskId?}`. Live execution additionally requires `driveWrite`, off by default, and the full Drive OAuth scope. A pasted Drive URL does not confer the per-file authorization that Google Picker provides for `drive.file`; this implementation does not claim otherwise.

A recipe validates the source document and destination folder, then uses native `files.copy` with the selected parent folder and new title. The native copy retains document structure/formatting instead of reconstructing a plain-text document. It never issues a write to the reference document. It changes only exact `{{title}}`, `{{context}}`, and `{{person}}` template placeholders in the copied file with revision-guarded Docs requests. If no context placeholder exists, it adds a visible “Provided context” section to the copy; arbitrary existing reference prose is retained rather than claimed to have been rewritten. Supplied values cannot contain the three reserved placeholders, avoiding cascading replacements. This is deterministic personalization, not model-generated research or prose.

Copy creation and personalization have separate durable operation records keyed by the same request ID. The copy record stores the confirmed new file ID before any personalization. A failed personalization read can resume using that same ID; an uncertain copy or write remains blocked for reconciliation. A new request ID deliberately means a new output. Receipts include exact input provenance, the output resource/URL, recipe ID, optional task ID, actual API/write counters and zero model/token calls. Partial output copies remain linked even if personalization fails.

The lead's request dispatcher should allow an explicit same-request recipe resume after verifying the original request fingerprint, rather than generating a new request ID for partial work. Re-entry is guarded by the copy/edit phase journals: accepted phases are not repeated and unknown phases are not retried.

## Unknown outcomes

A transport timeout, uncertain server response or malformed success response after a write is `unknown`, never success. A process crash leaving a pending send record also becomes unknown. There are no automatic mutation retries, including refresh-and-replay. Accepted Gmail responses mean Google accepted the send, not that delivery was confirmed. Reconcile unknown sends in Gmail before explicitly creating replacement work. There is intentionally no automatic “retry unknown” action.

## Synthetic validation

`createSyntheticGoogleAdapter()` in `synthetic.ts` supplies a network-free fictional adapter. It only accepts demo workspaces, reports Google as disconnected/unconfigured, labels messages and entity modes as demo, and exposes recorded mock calls for assertions. `MemoryGoogleStore` is test-only and is never a production fallback.

Run `npm test -- tests/google` for security, OAuth, local-loopback router, action, campaign, managed-write, scan-recovery, MIME/content, Daily pagination/DST/independent-failure and bounded-cache tests. These tests exercise injected responses. They do not establish that live OAuth, actual account policies, real sends, or real Google source mutations have been verified. No real credentials were available during implementation.

Drive Daily uses explicitly bound same-grant files and descendants of bound folders. Each invocation reads one file body or folder page, bounded to 40,000 characters/5 MiB per file, with a 2,000-entry selected traversal checkpoint. Drive, Gmail and Calendar report independent provider status. It does not enumerate broad Drive content merely because Daily is enabled. No model interpretation occurs in the adapter.

Daily provenance keys use the verified data subject (hashed in source IDs), remaining stable across same-account reconnection; per-grant cache/checkpoint namespaces still change. The lead must preserve canonical correction/tombstone history for same-account reconnects while removing stale active source context on a genuinely different account.
