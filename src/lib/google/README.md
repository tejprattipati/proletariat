# Google server integration

This module is server-only. Import `getGoogleStatus`, `executeGoogleAction`, `isGoogleAction`, and `configureGoogleIntegration` from `index.ts`; do not bundle these files into the GitHub Pages frontend. The backend mounts `createGoogleRouter({ authorizeRequest, getPermissions })` from `server/google-router.ts` at `/api/google`. The contract also exports `googleRouter`, which denies requests until `configureGoogleRouter` supplies its hooks.

## Deployment configuration

The owner supplies a Google Web application OAuth client. Enable the Drive, Gmail, Calendar, and Docs APIs used by the selected capabilities. Register the exact backend callback, for example `http://127.0.0.1:3001/api/google/callback` locally or `https://<backend-host>/api/google/callback` in a deployment. HTTPS is required except on loopback. Public Google scopes may require consent-screen verification; test users and workspace policy can affect which grants are available.

Server environment:

| Setting | Requirement |
| --- | --- |
| `GOOGLE_CLIENT_ID` | Web OAuth client ID supplied by the owner |
| `GOOGLE_CLIENT_SECRET` | Matching client secret; server only |
| `GOOGLE_REDIRECT_URI` | Exact registered backend URL ending in `/api/google/callback` |
| `TOKEN_ENCRYPTION_KEY` | Stable base64-encoded 32-byte key used by the lead's encrypted database token store |
| `DATA_DIR` | Private persistent runtime storage; use an absolute directory outside the repository for live deployment |
| `APP_ACCESS_TOKEN` | Backend owner authentication supplied by the lead's security middleware |
| `CORS_ORIGIN` | Explicit allowed frontend origins; credentialed OAuth setup must use the real frontend origin |
| `VITE_API_URL` | Public backend origin compiled into the Pages frontend; never place secrets in any `VITE_` variable |

No credentials are generated by this module's setup. It never reads browser, ChatGPT, or preexisting third-party credentials. OAuth access/refresh tokens must be encrypted at rest and must never be serialized in public workspace state, responses, logs, fixtures, or the repository. An optional `EncryptedFileTokenStore(absolutePath, base64Key, repositoryRoot)` is available for a single-account backend; it rejects repository paths and uses AES-256-GCM plus owner-only file permissions. Production currently uses the lead's injected encrypted database store.

## Required persistence hooks

`GoogleDependencies` in `contracts.ts` requires a token store and a durable Google store. `getPermissions()` is required for all provider API access, including cached reads and writes. Tests can additionally inject `fetch` and `now`.

- `tokenStore.load/save/clear`: use encrypted storage. Preserve every token field, including `connectionId`.
- `store.get/set/delete`: persist scans, cache entries, pagination cursors and OAuth state outside source control. A single `set` must replace its record atomically.
- `store.reserveOperation(key, fingerprint)`: atomically create a durable `pending` record, returning the existing record on collision. Never replace an existing fingerprint. Reservation must survive a process crash before returning.
- `store.finishOperation`: atomically replace the pending record with the observed accepted/failed/unknown outcome. Never expire or automatically reset send reservations.
- When a newly authorized `connectionId` differs from the stored grant, pause scheduled/running live campaigns, queued/running scans and automatic workflows before saving the new grant. The lead's SQLite implementation does this transactionally.

The integration serializes its own calls within a process. The lead must still serialize and persist workspace actions, save every `ActionResult`, and operate one backend/worker instance. This is a single-owner implementation, not a multi-user OAuth service.

## OAuth endpoints

Authenticated `POST /api/google/authorize` returns `{url}`. Navigate to that one-time backend start ticket; its first-party GET establishes an HttpOnly, SameSite=Lax callback cookie and redirects to Google. It avoids relying on third-party cookies from a cross-site Pages fetch. Ticket lifetime is one minute; OAuth state lifetime is ten minutes. Start tickets are process-local, so a server restart requires restarting consent.

The callback validates browser binding, one-time state, expiry, and PKCE before exchanging the code. Consent uses offline access and incremental scopes; the granted scope response is authoritative. Starting a new authorization or disconnecting invalidates an older pending authorization. Refreshes preserve refresh tokens and are serialized. Callback responses never contain token material.

Authenticated `GET /api/google/status` returns connection metadata. `POST /api/google/disconnect` deletes local tokens before attempting Google revocation. If revocation is not confirmed, the response explicitly says local tokens were removed and Google Account permissions need checking. GET disconnect is not supported.

## Capability and scope boundaries

| App permission | OAuth scope |
| --- | --- |
| `driveRead` | `drive.readonly` |
| `driveWrite` | `drive` (new native copies in selected destinations only) |
| `gmailRead` | `gmail.readonly` |
| `draft` | `gmail.compose` |
| `send` | `gmail.send` |
| `calendarWrite` | `calendar.events` |
| `docsWrite` | `documents` |

These are suffixes under `https://www.googleapis.com/auth/`. `driveFull`/`gmailFull` additionally permit broad scans; they do not independently authorize reads. `bulkSend` additionally permits campaign dispatch. Google scopes can be broader than an app capability: Gmail compose includes sending at Google's boundary, so the server independently checks `send` before any actual send. Changing a toggle does not grant an OAuth scope; reconnect when new scopes are needed.

Every integration action checks its supplied workspace permissions and the latest persisted permission flags. The transport rechecks relevant flags and granted scopes before each request. Caches, operation records, scan cursors and object bindings are isolated to one authorization grant. Reconnecting requires rebinding resource outputs, recreating old drafts, or rereading Calendar events; old grant IDs cannot silently target a different account.

## Action and worker behavior

- `resource.bind` verifies Google file metadata and resolves supported Drive/Docs/Sheets links without fetching arbitrary URLs. Resources use `google:drive:<fileId>`, retain document tab / sheet gid / managed named-range IDs, and have canonical direct URLs. Shortcuts resolve to their target file. Binding requires an explicit Google ID or link; this adapter does not guess files from ambiguous names.
- `resource.browse` accepts `parentId`, `q`, and optional `nextPage: true`. The next page cursor stays on the server per grant, parent and query. Each page merges into workspace resources. The message contains `More results are available.` only when another page exists. Authenticated `GET /api/google/resources` also exposes a typed paginated raw Drive metadata response.
- `scan.start`/`scan.resume` process one provider page per call, then return control. The worker must keep advancing queued/running jobs and respect paused jobs. Selected Drive coverage includes bound folder descendants; selected Gmail coverage includes explicitly linked live draft threads. Broad coverage requires the corresponding full-read flag. Drive scans currently index metadata, not document/PDF body extraction. Gmail scans read message content into the private provider cache. `analyzed` remains zero because no model analysis occurs here.
- Each scan page stores its changed resource metadata and progress with its cursor. On resume or the next sync, an uncommitted page is replayed before advancing, so a crash between adapter and workspace saves does not silently skip that page. A partially failed page is rolled back in workspace state and can be reread safely.
- `sync.run` uses Drive change tokens or Gmail history IDs once a complete broad scan has a checkpoint. Expired incremental history clears that checkpoint and returns `SYNC_CURSOR_EXPIRED`; an explicit new scan is required. A selected scan never silently expands to all data.
- Gmail primitives include message/thread reads, draft create/update, draft send and raw message send. MIME headers reject injection, and text is encoded as UTF-8/base64. Sending a draft submits the exact locally authorized content, avoiding sending an externally changed draft body or recipient.
- `draft.create/update`, `calendar.upsert`, and `docs.write` require `requestId`. The lead supplies one for every API action. Reusing a write identifier with different content fails. The journal also keys sends by draft or campaign-recipient ID so a new request ID cannot bypass a previous uncertain send.
- `campaign.start/resume` sends at most one pending unique recipient per call, with a persistent 1–60 messages/minute limiter. The worker must call again at the allowed interval while status is `running`. Scheduled campaigns wait until their time; unknown recipients pause the campaign. Permissions are checked after queue creation and again immediately before dispatch.
- `calendar.upsert` uses deterministic Google event IDs for creates and existing external IDs for updates. Timestamps must carry a timezone offset. Attendee notification emails are disabled with `sendUpdates=none`. `calendar.read` and `provider.listEvents` support bounded paginated reads using the configured calendar capability.
- `docs.write` only updates a preexisting managed named range in a bound live Google document with `role: output`. Bind `namedRangeId`, plus `tabId` when the document has multiple tabs. The adapter fetches the current revision, confirms that the named range exists in that tab, then sends `replaceNamedRangeContent` with `requiredRevisionId`. It never replaces the entire document or guesses a target tab/range.

## Reusable document recipes

Recipes persist their exact bound `referenceResourceId` and `destinationFolderId` in the shared workspace. The domain handles recipe creation/update; this module handles live `recipe.run {id,title,context,person?,taskId?}`. Live execution additionally requires `driveWrite`, off by default, and the full Drive OAuth scope. A pasted Drive URL does not confer the per-file authorization that Google Picker provides for `drive.file`; this implementation does not claim otherwise.

A recipe validates the source document and destination folder, then uses native `files.copy` with the selected parent folder and new title. The native copy retains document structure/formatting instead of reconstructing a plain-text document. It never issues a write to the reference document. It changes only exact `{{title}}`, `{{context}}`, and `{{person}}` template placeholders in the copied file with revision-guarded Docs requests. If no context placeholder exists, it adds a visible “Provided context” section to the copy; arbitrary existing reference prose is retained rather than claimed to have been rewritten. Supplied values cannot contain the three reserved placeholders, avoiding cascading replacements. This is deterministic personalization, not model-generated research or prose.

Copy creation and personalization have separate durable operation records keyed by the same request ID. The copy record stores the confirmed new file ID before any personalization. A failed personalization read can resume using that same ID; an uncertain copy or write remains blocked for reconciliation. A new request ID deliberately means a new output. Receipts include exact input provenance, the output resource/URL, recipe ID, optional task ID, actual API/write counters and zero model/token calls. Partial output copies remain linked even if personalization fails.

The lead's request dispatcher should allow an explicit same-request recipe resume after verifying the original request fingerprint, rather than generating a new request ID for partial work. Re-entry is guarded by the copy/edit phase journals: accepted phases are not repeated and unknown phases are not retried.

## Unknown outcomes

A transport timeout, uncertain server response or malformed success response after a write is `unknown`, never success. A process crash leaving a pending send record also becomes unknown. There are no automatic mutation retries, including refresh-and-replay. Accepted Gmail responses mean Google accepted the send, not that delivery was confirmed. Reconcile unknown sends in Gmail before explicitly creating replacement work. There is intentionally no automatic “retry unknown” action.

## Synthetic validation

`createSyntheticGoogleAdapter()` in `synthetic.ts` supplies a network-free fictional adapter. It only accepts demo workspaces, reports Google as disconnected/unconfigured, labels messages and entity modes as demo, and exposes recorded mock calls for assertions. `MemoryGoogleStore` is test-only and is never a production fallback.

Run `npm test -- tests/google` for security, OAuth, local-loopback router, action, campaign, managed-write and scan-recovery tests. These tests exercise injected responses. They do not establish that live OAuth, actual account policies, real sends, or real Google source mutations have been verified. No real credentials were available during implementation.
